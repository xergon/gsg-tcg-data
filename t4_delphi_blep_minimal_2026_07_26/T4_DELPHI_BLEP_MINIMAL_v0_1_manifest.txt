3. 🔴 C_evt IS NOT PRESENT. IT CANNOT BE DERIVED. T4 MUST SPECIFY IT.
================================================================================
The contract asked for header
  sample,source_record,run,event,C_evt,event_weight,selection_key_u64
The delivered file omits C_evt. This is deliberate: a wrong C_evt would produce a
confident wrong B_LEP, so nothing was invented.

WHY IT CANNOT BE DERIVED — this is a structural fact, not a missing-effort fact.
T4's stated DELPHI observable is a CHARGE-ORDERED, THRUST-HEMISPHERE CHIRALITY,
and its own required column list was: run; event; centre-of-mass energy;
hadronic-event flag; thrust and thrust-axis vector; charged-track momentum
vectors; charged-track charge; charged-track quality; event weight; generator
family.

The per-event table at commit a4225104 is an EVENT-LEVEL SUMMARY. It contains:
  - NO per-track momentum vectors
  - NO per-track charges
  - NO per-track quality flags
  - NO thrust value and NO thrust axis
It carries only event-scalar sums and two 3-vectors per event:
  P_charged = (sum_px_ch, sum_py_ch, sum_pz_ch)
  P_all     = (sum_px_all, sum_py_all, sum_pz_all)

A chirality is a PSEUDOSCALAR: it must be odd under spatial inversion. Building
one requires a triple product a.(b x c) of three linearly independent vectors
constructed from the event. Two vectors are available, and they are not even
independent in practice (P_all = P_charged + neutral sum). No mirror-odd
quantity can be formed from them. Every other delivered column (nctrk, ecm,
energies, cluster counts, ...) is a parity-EVEN scalar. Therefore C_evt is
provably unconstructible from this file — not merely undocumented.

WHAT T4 MUST DO — choose ONE:
 (a) DEFINE C_evt as an explicit arithmetic expression over the columns listed
     in section 5 of this manifest (they are all present in
     T4_DELPHI_PEREVENT_FULL_v0_1.csv.gz, which is mounted alongside). Cat will
     add the column, or T4 can compute it in-sandbox directly from the FULL
     file, which needs no further delivery. NOTE: any such C_evt will be
     parity-EVEN, so it is a generator-discrimination statistic, NOT a
     chirality. B_LEP would then score generator/detector agreement, and T4
     must decide whether that still answers its question.
 (b) DECLARE THE TRACK-LEVEL RE-EXTRACTION. If C_evt must be the true
     charge-ordered thrust-hemisphere chirality, the DELPHI short-DST must be
     re-read with the per-track loop retained (VECP momenta + charge + quality,
     plus a thrust computation). The reader that produced this table already
     builds, links and runs on the same machine; adding the track loop is a
     rebuild, not a new dataset. State the exact per-track columns and the
     exact chirality formula and Cat will re-run it. Do NOT re-request the
     CERN records — they are already fetched and adler32-verified.

4. DERIVATION OF EVERY COLUMN THAT IS PRESENT
================================================================================
sample
  Verbatim copy of the `sample` column of the source table (column 38 of 39).
  Asserted at build time to equal the file's own sample partition on every row.

source_record
  Constant per sample. The CERN Open Data record id of the source dataset:
    data     -> 81431   DELPHI_collision_short94_c2
                DOI 10.7483/OPENDATA.DELPHI.0XNE.G96F   (1994 collision data)
    mc_qqps  -> 81437   DELPHI_sh_qqps_e91.25_c94_2l_c2
                DOI 10.7483/OPENDATA.DELPHI.0HML.4DOT   (PYTHIA/JETSET shower, CERN production)
    mc_kk2f  -> 81344   DELPHI_sh_kk2f4146qqpy_e91.25_l94_2l_c2
                DOI 10.7483/OPENDATA.DELPHI.P4BN.GFID   (KK2f 4.14.6 + PYTHIA, Lyon production)

run
  Verbatim copy of the source `run` column (DELPHI IIIRUN), whitespace-stripped.
  ⚠ mc_kk2f run numbers are NEGATIVE (e.g. -40055). That is the DELPHI
  simulation convention as it appears in the DST, not a sign error.

event
  Verbatim copy of the source `evt` column (DELPHI IIIEVT, event number within
  the run), whitespace-stripped. Renamed evt -> event to match the contract.

event_weight
  CONSTANT 1.0 on every row, for all three samples.
  Justification: the source DSTs carry NO per-event generator weight. Both MC
  records are unweighted production samples and the collision data is unweighted
  by construction. 1.0 is therefore the correct value, not a placeholder — but
  it is DECLARED here so T4 can see that no weighting information was lost.
  Consequences: finite and > 0 on every row (contract requirement satisfied);
  sum of weights == row count per sample; weighted means degenerate to
  unweighted means.

selection_key_u64
  Deterministic 64-bit event key, defined exactly as
      s   = f"{sample}|{run}|{event}|T4_DELPHI_BLEP_v0_1"
      key = int(hashlib.sha256(s.encode()).hexdigest()[:16], 16)
  i.e. the top 16 hex digits (first 8 bytes) of the SHA-256 of that string,
  read big-endian as an unsigned 64-bit integer, printed in decimal.
  `run` and `event` are the whitespace-stripped decimal strings as they appear
  in this file (so the key is reproducible from this file alone).
  It is a STABLE, UNIFORMLY DISTRIBUTED, SAMPLE-SCOPED EVENT IDENTIFIER, for
  deduplication and for reproducible size-matched subsampling ("retain the
  smallest keys within a sample"), matching the construction T4 itself
  specified for the LHCb lane. It encodes NO selection decision and NO physics.
  🔴 If T4 intended selection_key_u64 to be a BITMASK OF SELECTION FLAGS rather
  than a hash key, say so and name the bits — this file's version must then be
  replaced, not reinterpreted.

  Verified: 453,204 distinct keys over 453,204 rows, no collisions.
